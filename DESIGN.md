# Manris design system

## Source of truth

Manris uses the official shadcn/ui `radix-nova` components, Radix primitives, a neutral base color, Inter typography, and Lucide icons. `frontend/components.json` records the component style and base; `frontend/src/app/globals.css` holds the theme tokens and `frontend/src/app/layout.tsx` loads Inter. Files under `frontend/src/components/ui` that come from the shadcn registry must match the source component. Install or refresh them with the project shadcn CLI. Do not add application variants, styles, or business logic to those files.

The living component catalog is `/design-system`. Update this document and that page before changing a shared visual rule on a feature page. After a feature page receives a direct design change, sync both references.

## Component usage

- Use installed shadcn components and their built-in `variant`, `size`, and composition APIs.
- Cards use the preset's `Card`, `CardHeader`, `CardTitle`, `CardDescription`, `CardContent`, and `CardAction` slots with their default radius, spacing, and inset. Form sections and dashboard chart panels do not reset the Card with `gap-0`, `p-0`, or custom header padding. Edge-to-edge tables and media may extend through a content wrapper while the Card source remains unchanged.
- Application action wrappers forward supported icon content into the stock `Button` with `data-icon="inline-start"`; they do not suppress icons supplied by a feature.
- Dropdown triggers and secondary import actions use the `outline` action treatment with a white surface in light mode, a visible border, and one contextual leading icon; omit a trailing chevron when the control's menu behavior is already clear from its placement and label. Action menus use one `DropdownMenuContent` surface with native `DropdownMenuItem` rows; do not nest a Card inside the popover or size the surface from an icon-only trigger.
- Dialog and form footers keep labeled Batal, Cancel, and Tutup actions on the trailing edge and use the stock outline treatment; page-specific overrides must not remove the outline border. Icon-only close affordances remain compact icon controls.
- Modal and drawer headers always pair a visible title with a concise `DialogDescription`, `AlertDialogDescription`, `SheetDescription`, or `DrawerDescription` subtitle. Subtitle or description text uses `text-secondary-foreground`, explains the purpose or consequence of the action, and follows sentence case.
- Right-side detail drawers use an 8px viewport inset, a compact `310px` desktop width with a viewport-safe max width, a solid `bg-card` inner surface, and the shared `smooth-shadow-ring-xl shadow-black smooth-ring-neutral-300/30` elevation. The close action stays in the top-right 28px hit area. Use `DrawerHeader`, scrollable `DrawerBody`, and optional `DrawerFooter` so long detail content never pushes the panel beyond the viewport. In the risk-detail drawer, keep the risk title at normal body weight and group source status, code, category, and version under `Properti sumber`. Detail metadata uses a stable label/value grid, `text-tertiary-foreground` only for identifiers, and wraps long category or title values instead of clipping them.
- Use `className` on a shadcn component only for page layout, such as grid placement, available width, alignment, or spacing between peer components. Do not override its color, type, padding, border, radius, elevation, icon size, or interaction state.
- In tables, the registry's `TableHead`, `TableCell`, and `TableRow` own typography, padding, surface, and borders. Header and body cells keep 8px horizontal spacing between columns, while the first and last cells use 16px at the outer table edges to align with Card content and pagination. Every primary title/name column—including `Risiko`, `Judul`, `Judul Piagam`, `Kejadian`, `Organisasi`, and equivalent labels—uses local `px-24` on its header and body cells for the same breathing room as the Register Risiko title column; keep the existing `colgroup` widths so the inset does not move neighboring columns. Every table header uses 13px text on the `#FAFAFA` `table-header` surface, while header labels use the `tertiary-foreground` token consistently across every page, including the Overview attention-risk ledger. Supporting body cells such as risk categories, linked risks, recorders, dates, and timestamps use `text-muted-foreground`; primary links and metrics may retain `text-foreground`, while statuses and risk scores keep their semantic treatment. The risk-level badge in the monitoring table's `Perubahan Skor` column reuses `levelToColor`, matching the risk-level badge in the risk-score form field. Compact identifiers such as event codes in ledger summaries and risk codes in confirmation-dialog metadata sit as secondary metadata below the primary label with `text-tertiary-foreground`. Risk codes below risk titles in Register Risiko use Inter 14px (`font-sans text-sm`) with `text-muted-foreground`; codes below mitigation plan titles in the Penanganan table remain 14px monospace. Long text columns normally use normal whitespace and word breaking to wrap within their cell; the primary action title in the Penanganan table is a one-line `truncate`, with its existing `px-24` cell inset preserved on both sides. Count columns use explicit `Jumlah ...` labels and are left-aligned by default; the `Jumlah risiko` column in the Kertas Kerja table is right-aligned. Page code may set column width, alignment, overflow, and sticky positioning.
- Typography hierarchy uses `text-foreground` for primary content, `text-muted-foreground` for supporting content, and `text-tertiary-foreground` (`#a3a3a3`) only for microcopy, captions, and disabled/low-priority text. Tertiary is not for normal body copy.
- Collection table adapters forward stock `TableHeader`, `TableRow`, and `TableHead` styling without a second density or cell inset. A standalone table reaches the Card edge through layout margins while the registry Card and Table source stays intact; action columns keep their width and alignment without a visible header label (the label remains screen-reader-only), sticky action columns inherit the opaque `table-header` surface, and pagination keeps its stock `CardFooter` spacing.
- Use application components for domain data, permissions, loading logic, and composition. They may wrap shadcn components but must not create a second visual style for a shadcn primitive.
- Collection pages compose `CollectionToolbar` with leading filters and trailing actions. The leading group uses `flex min-w-0 flex-1 flex-col gap-2 sm:flex-row sm:items-center`; persistent collection search uses the always-visible `CollectionSearchField` with the shared compact `h-8` geometry (32px), while `ExpandableSearchField` is reserved for intentionally space-constrained surfaces. Filter content composes `CollectionFilterPopover`, while the page supplies only its domain fields and handlers.
- The Register Risiko search field uses `placeholder:text-tertiary-foreground` for its low-priority prompt; keep entered search text at the standard input foreground.
- Render status with the stock shadcn `Badge` composition and its built-in variants. Draft states use the neutral gray `secondary` variant; pending/in-progress and medium severity use `border-transparent bg-blue-50 text-blue-700 dark:bg-blue-950 dark:text-blue-300`, final/success/done use `border-transparent bg-green-50 text-green-700 dark:bg-green-950 dark:text-green-300`, and cancelled states use `border-transparent bg-red-50 text-red-700 dark:bg-red-950 dark:text-red-300`. Do not add a second Badge component or custom tone API.
- Use shadcn `Card`, `Table`, `Sidebar`, `Dialog`, `Drawer`, `Sheet`, and form controls as the visual building blocks. Keep each component's required composition and accessibility parts, including overlay titles and avatar fallbacks.
- Forms compose `FieldGroup` and `Field`; use `FieldLabel`, `FieldDescription`, and `FieldError` for each control's text and validation. Search fields with a leading icon compose `InputGroup`, `InputGroupAddon`, and `InputGroupInput` so the icon reserves space instead of overlapping the placeholder. Selectable risk rows use a stock `FieldLabel` around a horizontal `Field`; align the checkbox with the first-line risk code and let the title wrap beneath it. The `/design-system` form example demonstrates both compositions.
- Login credential fields use a 36px height and white surface: the NIP field uses the stock `Input` with `h-9 bg-white dark:bg-white`, while Password uses `InputGroup` with the same outer geometry and a transparent `InputGroupInput`. Keep these as login-specific overrides; do not change the shared Input or InputGroup defaults.
- The login submit action uses the stock `Button` at `h-9 w-full rounded-full`; keep this pill-shaped, full-width treatment scoped to the login form.
- Mitigation progress reports use one standard text `Input` for the optional evidence URL; accept exactly one URL and keep its validation attached to the field.
- Use `Alert` for persistent form errors or success messages, `Spinner` for pending actions, and `Command` inside `Popover` for searchable option lists. Keep `CommandItem` inside `CommandGroup`.
- Shared empty, error, and loading states compose stock `Empty`, `Alert`, and `Spinner`. Search/filter empty states name the empty condition in normal weight and add a concise 12px subtitle with the next step, such as changing the query or adjusting filters. `CollectionEmptyState` uses a 14px medium title, a 12px muted subtitle, and a 4px title-to-subtitle gap; it accepts page-layout classes for a centered muted dashed surface when an upload/import empty state must match its adjacent upload box. Keep one surface boundary instead of nesting another empty-state card. Report links and persistent action bars compose stock `Card` and `Button`.
- Domain summaries, organization lists, and report surfaces use stock `Card` composition. A risk level may carry a risk data color; ordinary status and trend labels use stock `Badge` variants.
- Risk categories use the shared `RiskCategoryIndicator`: a small colored dot followed by the visible category label. The indicator has no border or background, uses one stable color per category, and never relies on color alone because the label remains visible. Use this composition in risk tables, overview lists, and risk detail summaries instead of rendering a bare category string.
- Secondary card content uses the semantic `secondary-card-surface` token (`#fbfbfb` in light mode) through `bg-secondary-card-surface`; use it for nested linked-record rows that need separation from the parent Card without inheriting the broader muted state surface.
- Document lists compose `CardContent`; criteria help triggers use stock `Button` and `Tooltip`; collapsible form sections use stock `Accordion` states.
- Collapsible card roots remove the Card's outer vertical inset; the trigger owns header spacing, while the body controls content inset so full-bleed tables can reach the card edge. Table content uses `CollapsibleCard.Body className="px-0"` at the call site; forms and summaries may keep the standard CardContent inset.
- The public risk guide presents process phases, document links, steps, and FAQs with stock `Card`, `Badge`, `Button`, and `Separator` compositions.
- Document processing task lanes and activity timelines compose stock `Card` and `Badge`. Their existing animated progress bar and running indicator remain application-owned motion for process data.
- Approval steps, report details, mobile working-paper rows, processing status, and risk-event review summaries use stock `Card` composition. Detail rows use 14px labels, `py-2`, and `gap-4` between labels and values by default; risk-event detail rows use `gap-8` (32px) for the label–value split. Preserve existing progress and hover motion in application code. Risk-event detail uses a desktop two-column split of roughly 55/45, with the Ringkasan card receiving a minimum 400px and `self-start` so linked-risk rows remain readable and the card height follows its content beside the event facts panel. Event severity and recorder belong in the main information card, while the Ringkasan card focuses only on linked risks. Each linked-risk row uses a subtle border, radius, and the existing secondary surface; the list wrapper itself remains unbordered. Shared `WarningCard` descriptions use `text-muted-foreground` while the warning title remains primary.
- Use Lucide for interface icons. Data charts compose the stock shadcn `ChartContainer` and `ChartTooltip`/`ChartTooltipContent` around Recharts primitives; use `ChartLegend`/`ChartLegendContent` for legends inside the plot, while existing contextual legends outside the plot remain page composition. Define series labels and colors in `ChartConfig` and give each chart an explicit height. Do not add a second chart rendering library or custom chart framework. The 5×5 risk heatmap remains a domain matrix rather than a Cartesian or pie chart, with visible axis labels and a legend.

## Theme and risk data

The application uses shadcn's neutral light theme: `primary` and `sidebar-primary` use neutral foreground tones, so stock `Badge` and `Button` default variants do not render teal. Draft badges use the neutral gray `secondary` variant; status classes provide blue for pending/in-progress, green for final/success/done, and red for cancelled without changing the global shadcn tokens. There is no theme toggle. Neutral dark tokens remain in the stylesheet for compatibility but are not exposed as a new application feature. Chart colors remain a separate data palette and do not style shadcn components.

The app shell, top bar, and main section use the preset `background` token (`#f1f1f1` in light mode). The sidebar and desktop logo section use the `sidebar` token (`#f1f1f1` in light mode), and navigation uses the stock Sidebar composition. Global `border`, `input`, `surface-border`, and `component-border` aliases resolve to `sidebar-border` (`#e3e3e3` in light mode) so structural borders share one color across the application. Stock Cards render their edge with a ring rather than a CSS border; the application sets that ring color to `sidebar-border` so the Card edge matches the sidebar divider.
Sidebar account and help actions use stock `SidebarMenuButton`, `DropdownMenu`, `Popover`, `Button`, `Avatar`, and `Badge` primitives. The navigation selection indicator keeps its existing motion in the application layer.
Sidebar navigation uses a 4px gap between items in one group. Stock `SidebarGroup` padding plus a 4px gap between groups separates sections, and the footer shares the navigation group's inline edge. Keep these layout gaps in application composition, leaving shadcn Sidebar source and animation timing unchanged.
Sidebar group labels use the `text-tertiary-foreground` token so navigation headings remain secondary to the active and actionable items. Inactive `SidebarNavItem` labels and icons use `text-muted-foreground`; active items use `text-sidebar-accent-foreground` while retaining the existing animated selection surface. The shared light-mode `sidebar-accent` surface is `oklch(0.93 0 0)`, slightly darker than the sidebar background, for a clearly visible but restrained hover and active-item state.
The Manris wordmark in the desktop top bar starts on the same inline edge as sidebar item icons. The brand and navigation share this alignment in the design-system sidebar preview. The logo section's right border and the topbar's bottom border use the `sidebar-border` token so the shell dividers share one color.
Plain page headings use Inter at `text-2xl font-semibold tracking-tight`; the heading rule does not alter shadcn component source.
Dashboard and collection KPI cards use a muted 12px metric title and supporting detail, with the numeric value remaining the visual focus at 24px. This application composition sets typography on its `CardTitle` and detail text without changing the shadcn Card source.
Dashboard KPI direction icons sit in the stock `CardAction` position at the top right, at 14px. Up uses the red risk token and down uses the green risk token for risk exposure context. Hide the icon while loading or on error. Current overview directions are supplied by page data rather than calculated from period comparisons; do not present them as measured changes until comparison data exists.
Risk form sections use `CardHeader` with `CardTitle` and `CardDescription`, followed by `CardContent`. Dashboard trend, priority, and heatmap cards share the same Card inset and heading position; their chart, table, and heatmap content may set width or overflow for data display. Trend-card legends use small round dots and sit directly below the header at the top of `CardContent`, while chart content follows beneath the legend. Narrative overview widgets use concise contextual subtitles: the attention list explains its highest-score prioritization, while the current heatmap explains its probability-impact distribution. The narrative overview orders KPI condition, trend change, attention risks, and the current heatmap. Its attention list uses the shared collection table header and stock `Table` cells, with the risk title as the primary label and code as secondary metadata. The current heatmap labels probability and impact axes, keeps a readable 12px legend, and places its multi-phase comparison action in `CardAction` instead of floating outside the surface. Risk-event detail cards use 14px CardTitle text so their section labels stay compact beside dense metadata.
The multi-phase heatmap comparison presents all six phases in one chronological row. Give each phase enough width for its 5×5 grid; on narrower viewports, keep the row and allow horizontal scrolling with the next phase visible at the edge. A visible subtitle under the dialog and Card title explains the comparison. Keep the legend within the dialog inset below the row, limit dialog height to the viewport, and leave the registry Dialog and heatmap cell source unchanged.

The only additional color scale is for risk data, including heatmaps, charts where color conveys level or direction, and risk-category indicators. Keep accessible text labels alongside color. The overview trend chart uses Tailwind 600-level color tokens: `blue-600` for total risk, followed by `cyan-600`, `green-600`, `yellow-600`, `orange-600`, and `red-600` for the risk levels; legend dots and chart lines use the same token mapping. Application-specific aliases may map legacy chart code to preset tokens while migration is underway; aliases must not restyle shadcn components.

## Layout and behavior

Preserve all existing routes, field data, role permissions, API behavior, navigation structure, and task order. Preserve the current information hierarchy and data density as far as the default components allow. Layout containers may use responsive grids, flex alignment, width limits, and overflow handling.

Desktop monitoring workspaces use a two-column grid with independent `self-start` alignment. The right-side "Simpulan Pemantauan" rail may remain sticky, but its offset must stay below the app chrome without exceeding the grid's initial top edge; this keeps the rail aligned when a left-column collapsible card expands. In the monitoring transaction table, place the risk code below the title in the `Risiko` cell and give that combined column `33%` width; keep the score-change column at `15%` and preserve the other column widths.

All existing animation behavior is preserved. Animation-only CSS or application wrappers may reproduce timing, easing, movement, and state transitions without changing registry component source. This is the sole exception to the no-visual-override rule. Respect the existing reduced-motion behavior. If an upstream component's animation conflicts with an existing animation, keep the existing behavior at the application layer.

Inbox approval filters use the stock shadcn `Tabs`, `TabsList`, and `TabsTrigger` primitives through the application `animated-tabs` wrapper. Its active indicator uses a `continuity transition` with `ease-in-out` timing so the selection slides smoothly between tabs while preserving spatial orientation. The `/inbox` navigation item is labeled `Tanda tangan` while the page title may retain its descriptive `Persetujuan & TTE` wording. Interaction motion rules for buttons and overlays live in `globals.css` and leave registry source untouched.
The same stylesheet retains input, checkbox, select chevron, Sidebar, and reduced-motion timings from the existing interface.
The application Drawer wrapper keeps right-side opening as the existing default, while bottom drawers explicitly request `direction="bottom"`. Right-side drawers use the floating 8px inset treatment and frosted scrim; bottom drawers retain the inset form geometry and dynamic-height behavior by composing the stock Drawer primitives. The `/design-system` Drawer detail example is the reference for metadata hierarchy and overflow behavior.
Multi-step incident forms use a centered Dialog with an 8px viewport inset, `max-w-3xl`, `rounded-2xl` corners, and a viewport-safe height. Align the header, scrollable body, and footer to one 16px content inset; separate the body with stock `Separator` components. Compose fields with `FieldGroup`, `Field`, and `FieldLabel`, use full-width Select triggers, and use `InputGroup` for search. Checkbox choices use the stock selectable `FieldLabel` and horizontal `Field` composition. When a step or conditional field changes, the modal grows or shrinks to its measured content height over 220ms with `--ease-out`, capped by the viewport; reduced motion disables the transition. The `/design-system` incident modal example demonstrates the same geometry and motion. The mitigation detail-to-report flow keeps one Dialog mounted: selecting `Lapor Progress` uses a `continuity transition`/`layout animation` to grow or shrink the same surface into the report form, and `Batal` returns to the detail state. It does not open a second modal.
Incident forms ask only for the event date using the stock shadcn `Calendar` inside `Popover`; do not show a time input. Keep the API's timestamp field compatible by assigning a stable local time internally, and present the event date without implying that a specific hour was entered.

## Migration and verification

Treat the current uncommitted worktree as the application baseline. Preserve ongoing feature and backend changes while migrating. Verify each migrated area with a production build and interaction review, then check the page against `/design-system` and this document. The revamp covers the public pages, app shell, and every feature route.
