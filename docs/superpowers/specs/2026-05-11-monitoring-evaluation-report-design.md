# Monitoring and Evaluation Report Export Design

## Context

Manris needs a new export for **Laporan Hasil Pemantauan dan Evaluasi Penerapan Manajemen Risiko** per unit kerja. The reference attachment is a 12-page Letter portrait PDF generated by TCPDF. The user confirmed that every section in the attachment must be included and that currently unavailable metadata should be rendered blank rather than blocking export.

The report is distinct from the existing compact formal report renderers. Its success criterion is visual and structural fidelity to the attachment: official cover, narrative sections, checklist tables, mitigation summary, closing text, footer, and signature layout.

## Scope

Add a new formal report type:

- Backend constant: `monitoring_evaluation_report`
- Frontend type option: `monitoring_evaluation_report`
- UI card label: `Laporan Hasil Pemantauan dan Evaluasi MR`
- Output: PDF download from the existing Formal Reports flow

The report must include:

- Cover with title, selected unit, semester, year, blank report number/date when unavailable, identity box, and BSrE footer.
- Opening letter addressed to the selected unit head.
- Sections 1-7: dasar pelaksanaan, tujuan, sasaran/ruang lingkup, metodologi, waktu, susunan tim, and unit identity.
- Section 8 with four subsections:
  - Kelengkapan dokumen pendukung pemantauan dan evaluasi manajemen risiko.
  - Pengujian atas kecukupan infrastruktur/rancangan proses MR.
  - Pengujian atas hasil pelaksanaan manajemen risiko.
  - Format pemantauan pelaksanaan mitigasi risiko.
- Sections 9-10: permasalahan and saran perbaikan.
- Closing paragraphs and signature block for kepala unit, ketua SKI, and tim reviu.
- Repeated footer text: `Dokumen ini telah ditandatangani secara elektronik menggunakan sertifikat elektronik yang diterbitkan oleh Balai Besar Sertifikasi Elektronik (BSrE), Badan Siber dan Sandi Negara (BSSN).`

Out of scope for this iteration:

- New database fields for organization address/code/location.
- New UI form for report metadata.
- Uploading or managing evidence documents.
- Real electronic signature integration for this new report.

## Data Rules

Use existing Manris data where available:

- Organization name from selected organization.
- Period from selected formal report period.
- Risk snapshot from `RiskRepository.ListCycleSnapshot`.
- Risk level counts from effective risk score/level.
- Mitigation plan count from `Risk.Mitigations`.
- Realized mitigation count from mitigation progress data if available in the loaded risk model; otherwise count recorded mitigations as the fallback for this iteration.
- Movement counts:
  - `Turun`: `BeforeMonitoringNilai > MonitoringResultNilai`
  - `Menetap`: equal or missing comparison when the risk is not new
  - `Naik`: `BeforeMonitoringNilai < MonitoringResultNilai`
  - `Baru`: risks with no previous/before-monitoring value

Render blank values for unavailable metadata:

- Report number and report date.
- Assignment letter number/date.
- Monitoring start/end dates.
- Coordinator, review lead, and review members.
- Organization code, location, address, leader name/NIP.
- Evidence URLs and manual analysis notes in checklist tables.
- Signature images/QR codes unless already available through a future data source.

Blank table cells should remain visually present. Where a sentence needs a value and the value is unavailable, use an empty phrase only if grammar remains acceptable; otherwise use `-`.

## Report Structure

### Cover

Use Letter portrait dimensions and a plain official style matching the attachment:

- Centered bold uppercase heading:
  - `LAPORAN HASIL PEMANTAUAN DAN EVALUASI`
  - `PENERAPAN MANAJEMEN RISIKO`
- Center block:
  - `PADA`
  - `SATUAN KERJA {organization}`
  - `{SEMESTER I/II}`
  - `TAHUN {year}`
- Left metadata block:
  - `Nomor :`
  - `Tanggal :`
- Bordered identity table:
  - `Satuan / Unit Kerja`
  - `Tahun Anggaran`
  - `Kode`
  - `Lokasi`
  - `Unit Eselon I`
- Footer at the bottom.

### Narrative Sections

Sections 1-7 use the attachment's wording as the template. Unit-specific values are substituted when available. Missing fields remain blank or `-`.

### Checklist Tables

Tables use thin black borders, white headers, Arial-like font, compact line height, and page flow matching the reference. The first implementation should prioritize content structure and row/column proportions over pixel-perfect hand positioning.

Checklist source rows are static templates for this iteration:

- Document completeness rows match the nine rows in the attachment.
- Infrastructure/process rows match the nested rows in the attachment.
- Results rows match the two main result categories in the attachment.

For rows that can be derived from system data, `Ya` may be checked automatically:

- Risk profile and risk assessment exists if risk count > 0.
- Mitigation plan exists if mitigation plan count > 0.
- Periodic monitoring report exists if monitoring/movement data exists.

For rows without a reliable system source, leave `Ya`, `Tidak`, `Uraian Kondisi`, and `Keterangan` blank.

### Mitigation Summary

Generate the mitigation summary table by risk level:

- Sangat Tinggi
- Tinggi
- Sedang
- Rendah
- Sangat Rendah
- Jumlah

Columns:

- No
- Uraian
- Jml Risiko
- Jml Rencana Mitigasi
- Jml Realisasi Mitigasi
- Jml Risiko Turun
- Jml Risiko Menetap
- Jml Risiko Naik
- Jml Risiko Baru

Below the table, render narrative conclusions for:

- Risiko sangat tinggi
- Risiko tinggi
- Risiko sedang
- Risiko rendah dan sangat rendah

The text follows the attachment but inserts computed counts and percentages.

### Closing and Signatures

Use the closing text from the attachment with the selected organization name. Signature block has two columns:

- Left: kepala unit title/name/NIP, blank QR/signature area.
- Right: Ketua SKI and Tim Reviu entries, blank signature/name/NIP fields unless future data exists.

## Architecture

### Backend

Extend the existing formal report flow:

- `backend/internal/domain/entity/formal_report.go`
  - Add `FormalReportTypeMonitoringEvaluation`.
- `backend/internal/usecase/formalreport/helpers.go`
  - Normalize and allow the new type.
- `backend/internal/usecase/formalreport/download.go`
  - Build a `MonitoringEvaluationReportData` payload.
  - Load risk snapshot using the same org/period rules as annual profile.
  - Compute mitigation summary and checklist status.
- `backend/internal/domain/entity/report.go`
  - Add typed payload structs for monitoring evaluation report data.
- `backend/internal/service/pdfreport/renderer.go`
  - Route the new report type to a dedicated renderer.
  - Keep renderer helpers private and focused.

The renderer should be added as a new cohesive section of `pdfreport`, with helper functions split into a new file if `renderer.go` grows too large. It should reuse existing style constants where possible, but can define report-specific table helpers to match the attachment.

### Frontend

Extend existing Formal Reports UI:

- Add `monitoring_evaluation_report` to `FormalReportType`.
- Add a new card to `formalReportDefinitions`.
- No metadata form in this iteration.
- Download behavior remains unchanged.

## Error Handling

- If the selected organization cannot be found, keep existing not-found behavior.
- If risk snapshot is empty, generate the report with zero counts and blank/checklist fallback values.
- If PDF rendering fails, return the existing formal report download error path.
- Do not fail because optional metadata is missing.

## Testing

Backend tests:

- Formal report type validation accepts `monitoring_evaluation_report`.
- Download use case populates only the monitoring evaluation payload for the new type.
- Mitigation summary computation handles:
  - risks across all levels,
  - no risks,
  - missing before/after monitoring values,
  - movement down/same/up/new.
- Renderer smoke test confirms PDF bytes are non-empty and contain recognizable text via `pdftotext` when available.

Frontend tests:

- Type definitions include the new report type.
- Formal Reports page definitions include the new card label.

Manual verification:

- Generate one report for a unit and compare page structure against the reference attachment.
- Confirm footer appears on each page.
- Confirm blank metadata cells remain visible instead of disappearing.

## Open Decisions

No blocking open decisions. Metadata remains blank for this iteration by user instruction. Future work may add a metadata form or organization master-data fields.
